Situation

Where the idea came from

This was my final project for Control Systems. I had seen plenty of smart locks and plenty of AI projects, but not really the two put together, and I was curious what that would look like. So I tried building one: a lock that doesn't just check whether a PIN is correct, but also pays attention to how someone is trying to get in.

02

Task

Connecting Hardware, Software, and AI.

For this project, I developed the Arduino firmware, Python backend, AI integration, and web dashboard. Working across the entire system helped me understand how each component communicates through serial protocols, APIs, and the control logic behind the smart lock.

03

Action

How the system works

The Arduino handles everything physical — the keypad, the lock itself, and counting failed attempts. Whenever something happens, it sends a short log over USB to a Python and Flask backend that's always listening. That backend takes a webcam photo with OpenCV, then passes the log to DeepSeek running locally through LM Studio so it can describe what it thinks is going on.

The part I had to think about most was trust. A small local model can be wrong in both directions, so I didn't want it deciding on its own. Now the hardware and the AI both have to agree before anything locks down. If the AI misses a threat the Arduino already flagged, Python locks anyway; if the AI raises an alarm the hardware never saw, Python ignores it. Everything shows up on a simple dashboard with the lock status, the AI's summary, the captured photo, and a manual override.

System architecture

Arduino + Keypad → Serial log → Flask backend → DeepSeek · LM Studio → Python guardrail → Lock / Lockdown 
# 2-way verification: hardware AND AI must agree.
# Prevents false lockdowns (AI hallucination) AND missed
# real threats (AI failure) — the single most important
# architectural decision in the system.
if hardware_demands_lockdown and ai_wants_lockdown:
    ai_action = "LOCKDOWN"   # both agree
elif hardware_demands_lockdown and not ai_wants_lockdown:
    ai_action = "LOCKDOWN"   # Python overrides the AI
elif not hardware_demands_lockdown and ai_wants_lockdown:
    ai_action = "NONE"       # Python blocks the hallucination
04

Result

How it turned out

It works end to end. Someone keying in wrong PINs repeatedly gets the lock shut, their photo captured, and a written summary of what happened on the dashboard, all running on a small 1.5B model on my own machine, with no internet needed. The model still hallucinates now and then, which is what pushed me to add the double-check in the first place. Building around something that isn't always right ended up being the most useful thing I learned here.
